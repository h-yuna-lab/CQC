# MLOps 문제 해결 기록

운영·배포 담당으로 다룬 문제를 상황 → 원인 → 조치 → 확인 순서로 정리했습니다. 수치와 판정은 당시 회차의 자료를 기준으로 합니다.

## 1. Jenkins와 호스트 Docker의 경로가 달랐던 문제

2026.10.02 테스트와 실패 복구 단계를 추가한 뒤 Jenkins #73~#77이 연속 실패했습니다. 요구사항 파일 부재, `No module named 'src'`, 배포 스크립트 부재 등 단계마다 다른 오류가 발생했습니다.

Jenkins는 컨테이너 안에서 호스트 Docker daemon을 사용하는 구조였습니다. `docker run -v`에 전달한 Jenkins 작업 폴더를 daemon이 호스트 경로로 해석해 빈 디렉터리가 연결됐고 테스트·배포 보조 스크립트가 사라졌습니다.

- 테스트 소스를 `docker cp`로 컨테이너에 복사하도록 수정
- Python 검사를 `python -m pytest`로 실행해 모듈 경로 일치
- 실제 디스크 지연에 영향을 받던 시간 시험을 가상 시계로 고정
- 배포 보조 스크립트 전달에서도 같은 경로 가정 제거

Jenkins #78·#79에서는 Python 287개·웹 46개 시험 통과와 배포 성공을 확인했습니다. 실패 회차는 교체 전 단계에서 멈춰 이전 성공 버전 #72를 유지했습니다. 이 숫자는 당시 회차에만 적용됩니다.

관련 구현: [Jenkinsfile](../../Jenkinsfile), [배포 상태 보존](../../scripts/ci/snapshot-compose.py).

근거: [팀 문제 해결 사례 12](../최종발표/개발%20중%20문제%20해결%20사례.md), [PR #81](https://github.com/yuudong123/CQC/pull/81), [PR #82](https://github.com/yuudong123/CQC/pull/82).

## 2. Simulator는 배포됐지만 검사 입력이 0건인 문제

배포 후 관제에서 입력이 증가하지 않았습니다. 컨테이너 실행 여부만으로는 실제 재생·Backend 전송 성공을 확인하지 못했습니다.

기동 시 데이터셋·저장 위치를 확인하고 자동 재생을 시작하도록 연결했습니다. `/health`는 재생 중이며 최근 30초 내 Backend 전송 성공이 있을 때 정상 상태를 반환합니다. Compose와 Jenkins Verify가 같은 조건을 확인하도록 맞췄습니다.

`running`·`lastSeenAt`을 배포 완료 조건에 넣어 정상 기동과 실제 검사 진행을 함께 확인하도록 바꿨습니다.

근거: [Simulator 배포·재생 계약](../wbs/reference/MO/simulator-deployment.md), [팀 문제 해결 사례 6](../최종발표/개발%20중%20문제%20해결%20사례.md).

## 3. 배포 코드와 로컬 검증 코드의 출처를 확인하기 어려운 문제

로컬 HEAD나 Jenkins 성공 SHA만으로 현재 컨테이너가 어떤 코드를 실행하는지 단정할 수 없었습니다. 운영 이미지에 SHA 레이블이 없으면 시험 결과에 배포 SHA를 연결하기 어려웠습니다.

Jenkins checkout SHA, 같은 빌드의 서비스별 digest, 현재 컨테이너 `.Image`와 Docker daemon을 대조했습니다. 미확인 배포 SHA를 로컬 코드 SHA로 대체하지 않았습니다.

2026.10.12 #139에서는 Backend·Inference·Simulator·웹 출처 4/4 일치를 확인했습니다. 10.13 설정 시험에서는 #147의 Backend·Inference·Simulator 3/3 일치를 확인하고 해당 이미지로 격리 시험을 수행했습니다.

관련 구현: [collect_mo09_followup.py](../../scripts/qa/collect_mo09_followup.py).

근거: [10.12 배포 확인](../wbs/results/qa-mo-20261012-stage2/README.md), [10.13 설정 시험](../wbs/results/qa-mo-sim04-sim05-20261013/README.md).

## 4. 오류 0건이어도 지연 기준을 넘은 정상 100건 시험

2026.10.12 저장 이력 100건에서 처리량 0.472362건/초, 재검사 9%, 시간 초과·추론 오류 0건을 관찰했습니다. 그러나 완료 간격 p90 2.5258초, 최대 5.755초로 기준을 넘었습니다.

중앙값·p90·최대 간격과 최대 지연 구간을 원자료에 연결했습니다. 측정 전후 컨테이너·이미지가 동일하고 빌드 감시 12회 모두 #139임을 확인했습니다. 새 빌드가 없었다는 사실을 다른 부하도 없었다는 증거로 확대하지 않았습니다.

QA-SIM-02·13 미충족 결과를 보존했습니다. 지연 원인은 이 회차에서 확정하지 못했으며 평균값이나 과거 통과 회차로 실패를 대신하지 않았습니다.

근거: [10.12 결과](../wbs/results/qa-mo-20261012-stage3/README.md), [100건 원자료](../wbs/results/qa-mo-20261012-stage3/normal-100-run/normal-100.json).

## 배운 점과 다음 개선

실제 실행 위치의 파일·권한·네트워크를 기준으로 원인을 찾고 프로세스 실행과 기능 동작을 함께 확인해야 했습니다. 시험 결과에는 입력 조건·실행 이미지·관찰 범위가 필요하며 부분 확인을 전체 통과로 바꾸지 않는 것이 중요했습니다.

다음에는 이미지 전송·해석·추론·저장 구간의 시간을 동일 검사 ID에 연결하고 이미지 빌드 단계에서 SHA를 자동 기록해 지연 분석과 배포 출처 확인을 단순화하고 싶습니다.
